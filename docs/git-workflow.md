## 2. 三条长期分支

| 分支 | 职责 | 准入与边界 |
|---|---|---|
| `dev` | 开发集成线 | 接收通过双审与相关验证的任务；允许继续开发下一版本，但不得把未完成任务当作可发布内容 |
| `release` | 一个版本的候选冻结与验收线 | 从明确的 `dev` 完整 SHA 冻结；冻结后只接收该版本的必要修复、测试与发布资料，不再整体合入前进中的 `dev` |
| `main` | 已发布稳定线 | 首次原生发布前保留原型基线；以后只接收通过发布验收的 `release` 或已验证的生产紧急补丁 |

三者永久保留，不删除、不重命名、不重写历史。其他分支均为有任务、有负责人、有结束条件的临时分支；标签不算长期分支。

常规方向：`任务分支 → dev → release → main`。`main → release`、`main → dev` 是发布完成或紧急补丁后的稳定内容回灌；`release → dev` 只用于明确的候选修复回流，不能代替下一轮冻结。

## 4. 主代理与子代理职责

主代理负责拆分依赖、派工、记录所有权、安排审阅和验证、跟踪进度、验收及触发集成。产品实现、原生工程实现、自动测试编写和测试修复均交给开发子代理。主代理可以编写规划、执行 Git 治理、检查构建和测试证据，但不能用直接编写产品实现绕过派工。此限制只约束主代理，不禁止受派开发子代理实现功能或修复测试。

创建工作树前，必须先登记任务与负责人、基线与合并目标、临时分支、文件所有权、依赖与门禁。创建后立即补齐工具返回的 worktree 标识、绝对路径、实际 HEAD 与状态，核对一致后再开始写入；提交、审阅、验证、合并与清理结果在对应动作完成后持续补齐：

| 字段 | 必须记录的内容 |
|---|---|
| 任务与负责人 | 稳定任务 ID、目标、开发子代理、两位审阅者、主代理 |
| 基线与目标 | `base_ref`、完整 `base_sha`、临时分支名、合并目标、目标分支完整 SHA |
| 工作树 | 原生受管 worktree 标识、工具返回的绝对目录、实际 HEAD、状态 |
| 写入所有权 | 允许编辑的明确目录/文件、禁止触碰的共享文件、接口依赖 |
| 依赖与门禁 | 前置任务合并 SHA、验收条件、自动检查与真机检查范围、已知限制 |
| 结果与生命周期 | 提交 SHA、两份审阅结果、验证证据、合并 SHA、归档及分支清理状态 |

依赖必须已经合入目标基线，或者已由主代理拆成先行的接口任务并验证后，后续任务才能开始。不得让一个代理基于另一个代理尚未审阅的本地文件开发，也不得用共享 worktree 传递未提交成果。

`*.xcodeproj/project.pbxproj`、共享 scheme、target/capability 配置、entitlements、依赖锁文件等高冲突工程文件指定单独所有者。其他代理提出变更需求，由该所有者串行落实。初始化与共享模型未完成时，不并行创建相互依赖的 iOS、watchOS 或同步实现；文件不重叠但接口依赖未满足，也不满足并行条件。

## 5. 临时分支与 worktree

| 任务 | 分支示例 | 起点 | 合并目标 |
|---|---|---|---|
| 常规功能 | `feat/match-engine` | 最新已验证 `dev` 的完整 SHA | `dev` |
| 开发修复 | `fix/event-replay` | 最新已验证 `dev` 的完整 SHA | `dev` |
| 测试 | `test/workout-recovery` | 最新已验证 `dev` 的完整 SHA | `dev` |
| 文档 | `docs/native-development-plan` | 最新已验证 `dev` 的完整 SHA | `dev` |
| 构建或维护 | `build/native-targets`、`chore/signing-setup` | 最新已验证 `dev` 的完整 SHA | `dev` |
| 候选修复 | `fix/rc-<version>-<issue>` | 当前冻结 `release` 的完整 SHA | `release`，再回流 `dev` |
| 生产紧急补丁 | `hotfix/<issue>` | 当前已发布 `main` 的完整 SHA | `main`，再回灌 `release`、`dev` |

名称使用小写 ASCII、数字和连字符，创建前通过 `git check-ref-format --branch`。不额外建立长期功能线或嵌套功能主分支。每任务一分支、一 worktree、一位写入负责人；并行任务必须拥有不重叠的写入范围。第二位代理审阅同一任务时可以只读，不能同时写入作者 worktree。

优先使用 Codex `create_worktree`：显式传入记录的完整 `ref`，使用返回目录，检查实际 HEAD，再在该目录创建或绑定任务临时分支；不要依赖默认 remote 分支。工具如产生附属临时引用，也一并登记和安全清理。先检查 `list_artifacts`，同一任务已有合适的受管 worktree 时复用，不重复创建。

仅当原生工具不可用时，才使用 Git worktree 后备：由主代理选择不与已有目录冲突的绝对路径，以已登记 SHA 创建临时分支及 worktree。若使用仓库内 `.worktrees/`，先确认已忽略；分支绑定、基线检查和所有权规则相同。不能用后备路径绕过原生工具对 primary、pinned、shared worktree 的保护拒绝。

工作树创建后记录基线检查结果；基线失败先归属到原有问题或当前任务，不能把失败隐去。依赖、缓存、构建目录和 DerivedData 隔离；设备、签名、CloudKit 容器等共享资源由主代理排期。工程路径尚未形成前不虚构已通过的 `xcodebuild` 命令。

目标 `dev` 前进后，作者在自己的任务分支以普通合并更新基线，并重新验证受影响部分。固定的原始 `base_sha` 保留不改，追加同步 SHA；不 rebase 或 amend 已共享历史。任务尚未分派时直接使用最新基线，不能因为旧任务先创建而复用陈旧 SHA。

## 6. 原子提交与审阅记录

默认格式为 `<type>: <subject>`。仅当多 target 已实际建立且范围清晰时，才允许 `ios`、`watch`、`core`、`backend` 作为 scope。一个提交表达一个可验证意图；直接相关实现、测试和必要文档可以同提，独立重构、格式化、工程配置或文档整理拆开。

示例：

```text
feat: 实现比赛事件持久化与回放
fix: 修正暂停跨越结束时间时的出场统计
test: 覆盖手表迟到事件的去重行为
docs: 记录原生开发与发布流程
build: 建立 iPhone 与 Apple Watch targets
chore: merge feat/match-engine into dev
chore: freeze release vX.Y.Z-rc.1
chore: release vX.Y.Z
```

scope 不用于任务类型或合并操作，例如不使用 `chore(merge)`。普通描述用具体动宾短语，不使用 `WIP`、`update` 或“调整代码”；英文 subject 用小写动词开头、末尾无句号。

使用明确路径暂存，检查 `git diff --cached`，不使用 `git add .`、`git add -A`，不混入他人改动。提交 body 写实际执行的验证、结果和必要限制，例如：

```text
Verification: <实际命令或真机步骤>
Result: <实际通过/失败数量或观察结果>
Device: <涉及真机时的设备、系统、构建 SHA>
Limitations: <未验证项及原因；无则写无>
```

尚未执行就写“未执行”及原因，不能复制计划命令冒充验证证据。纯文档任务记录链接、事实和差异检查，真机检查注明不适用及理由。

未使用 PR 时使用本地合并审阅记录；未来有 PR 时写入同样字段：原始 base SHA、当前目标 SHA、任务 head SHA、路径所有权、两位审阅者、实际验证及限制、必要截图/日志位置、最终 merge SHA。每次修改 head、目标分支或冲突处理后，重新确认受影响审阅与验证，不能复用旧 SHA 的通过结论。

## 7. 合入 dev 的门禁与方式

1. 作者自检任务范围、敏感内容、暂存路径及相关自动测试，交付具体 head SHA。
2. 第一位独立审阅者检查业务正确性、架构、数据与接口、所有权；第二位独立审阅者检查需求一致性、测试覆盖、回归与集成证据。作者自审不计入双审，未解决的阻塞问题不得合并。
3. 对本次行为相关的检查完成后才集成：共享事件核心需要确定性与边界测试；iOS/watchOS 改动需要相应构建和界面检查；HealthKit、GPS、后台/恢复、WatchConnectivity、锁与离线同步等真实能力需要配对 iPhone/Apple Watch 或相关后台的实际验证。模拟器或浏览器 mock 不能替代这些真机证据。纯文档及不涉及设备的任务可记录真机“不适用”与理由。
4. 主代理在独立集成上下文核对当前目标 SHA，触发 `git merge --no-ff <task-branch>`。不由开发子代理自行把任务推进长期分支。合并冲突由拥有相关文件的代理处理；主代理重新安排审阅和受影响验证。
5. 合并后针对实际 merge SHA 再做集成检查；失败时在临时修复分支形成新修复或 `revert`，不能通过 reset、移动分支或改写合并历史隐藏失败。通过后才允许依赖该成果的任务开始。

统一使用 `--no-ff`，不 squash：保留原始任务 SHA、审阅证据和合并边界，也能以祖先关系验证分支已安全接收。`dev → release`、`release → main` 及回流同样使用此方式。合并消息仍采用合法 Conventional Commit，不沿用历史 `merge(...)`、`milestone(...)` 等非标准 type。

## 8. 冻结、候选修复与正式晋级

主代理为 `release` 持有一个排他的候选记录：版本号、冻结的完整 `dev` SHA、当前候选 head、RC 标签、候选修复队列、验证结果及发布状态。同一时间最多一个活动版本；`dev` 可以继续前进，但下一版本不得进入 `release`。

### 冻结

1. 确认上一候选已经发布并完成回流，或已经按下述取消流程闭环；不存在未合并的候选修复、未完成审阅或占用 `release` 的任务。
2. 从 `dev` 选择明确的已验证完整 SHA，审查本次 `main..候选` 的提交和最终树差异。`dev` 作为完整冻结来源，必须整体满足该版范围；若混有不应发布的内容，先在 `dev` 处理范围，或推迟冻结，不能凭“测试时没点到”让其进入候选。
3. 将该完整 SHA 以 `--no-ff` 合入 `release`，完成版本配置、发布说明、自动回归及相关真机验收。创建 annotated `vX.Y.Z-rc.N` 标签，绑定实际候选 SHA；每次修改形成新 RC，不移动旧标签。

### 冻结期间的修复

修复任务从当前 `release` SHA 开始，独立分支及 worktree，只处理该候选缺陷。通过同样的双审与验证后先合入 `release`，再把同一修复分支合入 `dev`，核对冲突后的行为等价并重测。不能整体合入前进中的 `dev` 获取修复，否则会泄漏下一版本内容。

候选有在途修复时不能提升 `main`，也不能冻结下一个版本。修复如需依赖下一版本尚未完成的能力，主代理必须缩小修复、回退有问题内容或重新界定候选，不能将两个版本混跑。RC 验证失效项必须重跑，记录新 head SHA。

### 晋级 main

主代理准备绑定具体版本、完整候选 SHA、差异、双审、自动与真机证据及已知限制的发布检查包，在用户既有任务授权范围内执行本地晋级与合并，不重复请求许可。旧协议的 `before-main-promotion` 不自动增加一次人工审批；远端已有强制保护仍须满足。推送、上传、部署或外部分发若缺乏既有授权，先备齐可审阅结果，再请求该项授权；规划或本地推进授权不能扩展为外部发布授权。

在已授权的本地任务范围内，将验收的 `release` 以 `--no-ff` 合入 `main`，对实际 `main` merge SHA 做最终构建与冒烟，再创建不可移动的 annotated `vX.Y.Z` 标签。核对最终树只含该版内容；标签、构建、发布说明均绑定实际 SHA。合入、打标签或本地构建不代表已上传 TestFlight/App Store 或已部署后台。

完成后将 `main` 合回 `release`、`dev`，验证稳定修复与版本信息一致，再关闭候选记录。下一轮只能在回流结束、在途候选任务为零时开始。三条长期分支均保留，不能删除重建 `release` 来复用发布线。

### 取消候选

暂停冻结新版本，先关闭、合并或明确撤销全部候选修复任务，并保存候选标签和原因。由主代理制定普通 `revert` 提交，使 `release` 相对当前稳定 `main` 不再携带被取消的产品差异，经双审和验证后才解锁下一候选；不 reset 或强行重指 `release`。这些撤销不机械回流到 `dev`；以后重新引入已被撤销的内容，必须显式恢复、重新审阅验证，不能假定普通 merge 会自动重放。无法确认取消差异已闭环时继续锁住发布线。

## 9. main 紧急补丁与回灌

从当前已发布 `main` SHA 创建 `hotfix/<issue>`，只包含必要修复和回归测试。经双审、相关自动与真机验证后，在既有任务授权范围内以 `--no-ff` 合入 `main`，复核 merge SHA 并创建新的 PATCH 标签；不能把整个 `dev` 或活动候选并入 `main` 修生产问题。外部分发沿用上一节的授权规则。

随后把 `main` 的稳定内容分别合回 `release`、`dev`。如 `release` 正在验证其他版本，保留其版本号和范围、增加新 RC 并重做受影响验收；稳定补丁回灌不等于接收下一版本。若原候选修复已经包含同类修复，由相关所有者解决冲突并证明两边行为一致，不能仅凭 Git 无冲突宣称完成。两处回流和验证未完成前，保留 hotfix 分支与台账，不开始下一次冻结。

## 10. worktree 归档与临时分支删除

每个任务的顺序固定为：完成验证与双审 → 主代理合并 → 验证实际合并结果 → 安全归档 worktree → 删除临时分支。清理失败时保留分支并记录原因，不为追求“只剩三条”而强删。

清理前逐项核对：

1. 临时分支不属于 `dev`、`release`、`main`；任务所有者已停止写入，无活跃子代理、后续任务、打开 PR、脚本或其他 worktree 依赖其分支名或目录。用 `git worktree list --porcelain` 与任务台账核对全部占用，不只看当前目录。
2. 记录完整 task tip 与各必需目标的 merge SHA；对每个目标执行祖先关系检查，证明 task tip 已被接收。生产补丁和候选修复必须完成其所有回流目标，不能只检查一个目标。检查是否还有未合并的唯一任务提交；失败就保留分支。
3. 检查已暂存、修改、未跟踪文件及 ignored 文件清单；未跟踪内容不能仅凭“未提交”丢弃。依赖缓存可以重建，但必要的签名文件、证书、描述文件、环境配置、测试证据或其他 ignored 资产必须先安全保存到适当的持久位置，核实可恢复，不能为保存它们而提交凭证。
4. 检查其他引用与依赖，只删除当前任务的临时分支及经核实可删的附属临时引用；永久分支、发布标签、其他任务引用和 Codex 的恢复快照引用均保留。已合并提交仍被长期分支引用是正常状态；这里检查的是未完成工作对临时分支/目录的依赖。
5. 对原生受管 worktree 使用 `list_artifacts` 获得精确 identity，再调用 `archive_worktree`；核对归档成功及可恢复信息。该工具不保留 ignored 文件，不能用归档替代上一步保存。归档产生的恢复快照应保留，不能当作“无用唯一提交”删除。
6. 归档成功后重新确认任务分支 tip 未改变、没有 worktree 占用，并用 `git branch -d <task-branch>` 删除本地临时分支；若安全删除拒绝，查明原因，不改用 `-D`。工具若已移除临时引用，先核对事实，不重复操作。
7. 未来临时分支曾推送到远程时，确认 PR 已合并/关闭、远程 tip 与记录一致且不存在他人新提交或依赖，再按已授权的远程清理操作删除该临时远程分支；当前没有已推送的临时远程分支，不执行。不能把删除远程分支扩展为删除标签或长期分支。

原生归档工具确实不可用时，只对已经完成上述检查的非受管后备 worktree 使用 `git worktree remove`，不加 `--force`。必要的 stale 元数据先用 `prune --dry-run` 核对，确认不影响他人后再处理；不使用 `rm -rf` 代替 worktree 生命周期。

## 11. 本地执行边界与未来远程保护

当前 `remote.mode = configured-write-authorized`：`origin = https://github.com/bskle/football-record.git` 为用户已接受的 public 仓库。用户最新“公开就公开暂时没事”覆盖此前 private 意向；无需等待可见性改为 private。主代理已在可访问系统 keyring 与网络的上下文核对 `gh auth status`（已登录、HTTPS）及 `gh repo view`（`PUBLIC` / `ADMIN`），并成功执行 `gh auth setup-git --hostname github.com`。受限 sandbox 无法访问系统凭据或网络时的认证失败不能覆盖这次有效核对。2026-10-15 已按授权以 `git push --atomic -u origin main dev release refs/tags/prototype-baseline-20261015` 完成首次同步并核对远端引用；GIT-003历史登记的远端 `dev` 为M2记录UI合并 `2e1f9c42f4398a50b66765a0f37f90ced95a7554`；GIT-004核对时已同步并核对到017实际合并 `b0070c90d91bf9d7741b7a7ed24165f1ad27383d`，远端仅三条长期分支，默认分支为 `main`。不自动推送其他临时分支或标签。代码同步不代表签名、真机验收、TestFlight / App Store 分发或原生发布完成；PR、CI 与服务端保护规则尚未配置。

首次推送前核对实际 remote、待推引用及预期 SHA，推送后核对远端结果；后续交付仍须重新识别 upstream、默认分支、保护规则与写权限。当前已核对的登录及管理员权限不证明保护或 CI 已配置。三条长期分支应保护禁止直接推送、删除和历史改写；`dev` 要求双审与相关自动检查，`release` 还要求版本候选验收，`main` 要求发布证据并遵守服务端既有审批规则。真机验证无法自动化的部分以绑定 SHA 的记录作为必需审阅证据。provider 不支持某项强制规则时写明限制，由主代理在流程中执行，不能宣称服务端已经强制。

禁止 `git reset --hard`、`git clean -fd`、`git checkout -- <path>`、`git branch -D`、任何强推（包括 `--force-with-lease`）、改写共享提交、移动或覆盖已发布标签、自动 stash 来源不明的修改，以及删除三条长期分支。共享错误用新修复或 `git revert`，没有授权不推送、不上传、不部署、不发布。
